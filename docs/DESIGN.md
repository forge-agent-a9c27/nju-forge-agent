# Forge 设计说明

## 目标

Forge 不是现成 agent 产品的 UI，也没有调用 agent 框架。核心问题被拆成四个可独立验证的边界：模型协议、对话状态、工具运行时、本地副作用。模型负责语义决策，程序负责确定性约束；两者只通过结构化消息通信。

```text
用户任务
   │
   ▼
Agent Loop ──请求──> OpenAI-compatible 模型
   ▲                         │
   │                         │ tool_calls
   │ tool observations       ▼
Context Manager <──── Tool Runtime
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          文件边界     编辑事务     命令风控
```

依赖方向是单向的：`protocol.py` 定义数据对象；`model.py` 只做 HTTP 与响应解析；`workspace.py` 只管理路径和原子编辑；`tools.py` 把本地能力声明成 JSON Schema；`context.py` 管理历史；`agent.py` 组合闭环；`cli.py` 负责输入、审批和展示。

## 一次循环如何运转

1. 用户消息写入 `Conversation`。
2. 超过预算时，按完整的 assistant + tool results 事务分组压缩，避免产生“有 tool call、无 tool result”的非法历史。
3. `OpenAICompatibleClient` 把消息与工具 Schema 直接 POST 给模型厂商。429、超时和 5xx 使用有上限的指数退避。
4. 解析原生 `tool_calls`；少数兼容网关若把调用降级成文本，也只接受显式 `<tool_call>` JSON 标签，避免误判普通代码块。
5. `ToolRuntime` 做 JSON 解码、字段白名单和类型校验，再执行本地实现。任何异常都会变成 `[ERROR]` observation 返回模型，而不会击穿循环。
6. 模型收到真实结果后继续决策。连续三次完全相同的调用批次会被熔断；达到步数上限后撤掉全部工具，只允许一次事实性总结。
7. 模型不再调用工具时，其文本即最终答复。

## 工具与副作用

`list_files`、`read_file`、`search_files` 没有调用外部服务。读取结果带行号、总行数和 SHA-256。`write_file` 使用同目录临时文件、`fsync` 和 `os.replace` 原子替换；`edit_file` 要求精确旧文本，默认拒绝多处匹配。可选 `expected_sha256` 实现乐观并发控制，防止模型依据过期内容覆盖用户的新修改。

每次成功编辑都会在被 Git 忽略的 `.forge/journal` 保存修改前内容、前后哈希和事务号。`undo_edit` 只有在当前哈希仍等于该事务的后置哈希时才恢复，因而不会回滚掉更晚的人工修改。

`run_command` 固定工作目录，限制时长和输出长度，并从子进程环境中剔除名称含 key、token、secret、password 等字段的变量。命令分三级：常见检查/测试直接运行；删除、联网、安装、Git 写操作等默认确认；磁盘格式化、关机、根目录递归删除等永久阻断。这是护栏而非沙箱，文档明确保留了边界。

## 路径与凭据

所有模型可见文件路径在 `resolve()` 后必须仍位于工作区。这个检查也覆盖利用 `..`、绝对路径和已有符号链接的逃逸。`.git`、`.forge`、`.env*`、私钥与常见凭据文件对模型隐藏且不可读写。API key 只存在于主进程配置中，不进入系统提示、tool observation 或命令子进程。

## 上下文策略

Forge 不依赖某一家 tokenizer，而用偏保守的中英文字符估算。达到预算后保留最新事务，将旧用户目标、助手结论、工具名称/参数和结果压成有界的确定性摘要。摘要标记工具内容为“不可信观察”，并最多保留最近 40 条证据。选择确定性压缩而非再次调用模型有三点考虑：不额外收费、失败路径更少、保留内容可预测。代价是语义提炼不如模型摘要灵活，因此最新原文始终优先保留。

## 为什么这样设计

- 原始 HTTP 而非厂商 SDK：题目允许 SDK，但标准库实现更容易证明核心逻辑确实自行完成，也减少安装失败。不过它只承诺 Chat Completions 兼容，不假装覆盖所有厂商私有协议。
- 顺序执行工具：模型可以一次返回多个调用，但写入和命令按顺序执行，使观察顺序、事务和审批可复现。只读并行可降低延迟，但会增加取消与输出排序复杂度，当前规模收益有限。
- 原子小编辑加乐观锁：比“每次重写整个仓库”更可审计；失败时给模型精确反馈。
- 人在回路而非全面禁止命令：coding agent 必须能安装、测试和操作 Git，但默认应让用户掌握不可逆或外部副作用。

## 错误与终止矩阵

| 场景 | 行为 |
|---|---|
| 参数 JSON 损坏/字段错误 | 返回工具错误，模型可修正 |
| 文件冲突/越界/敏感路径 | 拒绝且说明边界 |
| 命令失败/超时/输出过长 | 返回退出码、部分输出或头尾摘要 |
| API 临时错误 | 退避重试，超限后终止当前任务 |
| 重复工具批次 | 第三次返回 loop guard |
| 达到最大步数 | 工具置空，生成一次最终交接 |
| Ctrl+C | 补齐悬空 tool result，保持下轮协议有效 |

## 已知边界与可演进方向

当前版本没有 OS 级容器隔离、流式输出、语义向量检索和多 agent 并行。后续优先级是：以容器执行未知命令；对只读工具做并发调度；增加 Responses/Anthropic 原生适配器；用增量索引替代大仓库逐文件搜索；为编辑 journal 增加会话级 checkpoint。它们都可以在现有边界后扩展，不需要重写 agent 循环。
